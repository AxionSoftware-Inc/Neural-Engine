# V0.22 300M/500M scaling and route-coverage study

V0.22 runs the sparse `LazyAdamW` path on the 300M and 500M configurations
from `taklif.md`. The goal is to separate hardware feasibility from useful
quality scaling: a larger circuit bank should improve the task, not merely add
unused rows.

All runs used an NVIDIA GeForce RTX 3060, CUDA, seed 17, task-balanced
batches, numeric value encoding, three recurrent steps, and eight active
circuits. The 500M coverage variant adds
`routing_coverage_weight: 0.01` and temperature `0.25`.

## Reproduction

```powershell
python train.py --config configs/ne_300m_screen_lazy.yaml --steps 5000 --device cuda --balanced-train --run-id ne300m_lazy_quality_5000 --output results/runs --log-every 500 --checkpoint results/checkpoints/ne300m_lazy_quality_5000.pt
python train.py --config configs/ne_500m_screen_lazy.yaml --steps 200 --device cuda --balanced-train --run-id ne500m_lazy_screen_200 --output results/runs --log-every 50 --checkpoint results/checkpoints/ne500m_lazy_screen_200.pt
python train.py --config configs/ne_500m_screen_lazy.yaml --steps 5000 --device cuda --balanced-train --run-id ne500m_lazy_quality_5000 --output results/runs --log-every 500 --checkpoint results/checkpoints/ne500m_lazy_quality_5000.pt
python train.py --config configs/ne_500m_screen_lazy_coverage.yaml --steps 1000 --device cuda --balanced-train --run-id ne500m_lazy_coverage_pilot_1000 --output results/runs --log-every 250 --checkpoint results/checkpoints/ne500m_lazy_coverage_pilot_1000.pt
python train.py --config configs/ne_500m_screen_lazy_coverage.yaml --steps 5000 --device cuda --balanced-train --run-id ne500m_lazy_coverage_quality_5000 --output results/runs --log-every 500 --checkpoint results/checkpoints/ne500m_lazy_coverage_quality_5000.pt
```

The inference active-budget checks were run with:

```powershell
python analyze_active_budget.py --checkpoint results/checkpoints/ne300m_lazy_quality_5000.pt --device cuda --active-circuits 4 8 16 --examples-per-task 64 --batch-size 128 --iterations 50 --output results/runs/ne300m_lazy_quality_active_budget.json
python analyze_active_budget.py --checkpoint results/checkpoints/ne500m_lazy_coverage_quality_5000.pt --device cuda --active-circuits 4 8 --examples-per-task 64 --batch-size 128 --iterations 50 --output results/runs/ne500m_lazy_coverage_active_budget.json
```

## Results

| Run | Params | Steps | Batch | Exact accuracy | Avg steps | Dead circuits | Used circuits | Train time | Samples/s | Peak VRAM |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| NE-300M lazy | 299.544M | 5,000 | 16 | **56.80%** | 1.597 | 56.06% | 10,018 | 347.7 s | **230.1** | 7,710 MiB |
| NE-500M lazy, no coverage | 505.832M | 5,000 | 8 | 44.32% | 1.000 | 67.49% | 12,548 | 509.6 s | **78.5** | 9,547 MiB |
| NE-500M lazy + coverage | 505.832M | 5,000 | 8 | 44.11% | 1.000 | **60.00%** | 15,439 | 555.4 s | 72.0 | 9,565 MiB |

The coverage pilot after 1,000 steps reached 24.97% accuracy, used 17,385
circuits, and lowered the dead fraction to 54.96%. After 5,000 steps the
regularizer still improved utilization relative to the no-coverage run, but
did not improve final quality. Its routing entropy was 9.37 versus 8.75 for
the no-coverage run.

The 500M feasibility screen completed 200 steps at 77.2 samples/s and 7,114
MiB peak VRAM, so the model fits safely on the test GPU. The full run used
9,547–9,565 MiB, leaving roughly 2.4 GiB headroom on a 12 GiB card.

## Active-path and inference check

On the 300M checkpoint, active budgets 4, 8, and 16 produced 56.56%, 56.56%,
and 56.67% full accuracy respectively. Throughput was 14,650, 14,295, and
13,180 samples/s, so increasing the active budget beyond eight adds cost
without a measurable quality gain. Average active parameters remained about
2.0–2.2M, or 0.65–0.74% of the 299.5M total.

On the 500M coverage checkpoint, active budgets 4 and 8 produced 44.79% and
44.69% full accuracy, with 32,030 and 29,531 samples/s respectively. The
active path was about 1.98M parameters, only 0.39% of the 505.8M total, but
the extra stored capacity did not recover deeper tasks.

## Interpretation

The architecture is hardware-feasible at 500M with the sparse optimizer, but
the current scaling rule is not useful: it grows the circuit bank while the
training stream touches too few rows and remains mostly one-step. The 300M
checkpoint is the strongest large-model result so far. The 500M result must
not be presented as a quality improvement over 300M.

This also rules out a simple coverage-loss-only fix. Coverage spreads routing
more evenly, but depth-2 and depth-3 accuracy remain near chance and the final
exact accuracy is unchanged. The next experiment should change the training
schedule or parameterization: start from a smaller active circuit bank and
expand capacity gradually, or share/factorize circuit parameters so new rows
can inherit useful features. Only after that should another 500M quality run
be considered.
